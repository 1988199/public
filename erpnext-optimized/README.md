# ERPNext V16 优化运行镜像

基于已验证标准单容器镜像的独立优化发行版，镜像包为 `ghcr.io/1988199/erpnext-optimized`。优化内容不覆盖到 `erpnext-single` 镜像包，不包含企业数据或私有配置。

## 自动更新与发布

运行修订20261026.1的备份、日志、应用就绪、停机及低开销改进当前属于源码候选，独立验证、不覆盖已发布同版本标签；正式功能随下一次ERPNext新版本发布。使用前请核对运行修订号。参数与恢复边界见[运行维护](docs/运行维护.md)，优化范围与合成基准见[性能优化说明](docs/性能优化说明.md)。

每天的 ERPNext 检查由 [标准基础流程](../.github/workflows/erpnext-auto-build.yml) 执行。只有 ERPNext 自身 V16 稳定版本前进才构建标准基础镜像；该流程成功后自动衔接 [优化发布流程](../.github/workflows/erpnext-optimized.yml)。优化版也独立比较自己的已发布 ERPNext 版本，不因 Frappe、HRMS、CRM 单独更新或源码推送而重发同版本。

基础镜像已验证后，优化脚本固定其 GHCR 分发摘要，同步官方应用版本和 CRM 提交，复用 SQLite、显式迁移及长短队列等优化。初始化、索引、重启和升级保护测试通过后，才发布 `V版本-opt-运行修订号`、`V版本`、`latest` 和不可变构建标识；成功发布后才记录优化版清单。若优化阶段失败，清单不前进，后续每日检查成功后会重试待发布版本。手动运行优化工作流也不绕过版本门禁。

已发布的应用版本和运行修订以[发行清单](docker/manifest.json)为准；它与候选源码中的 `docker/RUNTIME_REVISION` 分开维护。镜像提供 `latest`、`V版本` 及带运行修订的标签。不要把工作流检查成功理解为已生成新镜像：相同ERPNext版本会跳过发布。

下文描述源码的默认初始化参数；使用历史镜像时应核对该镜像的运行修订及对应版本说明，不将新源码参数误用于旧镜像。本轮不重发已发布标签。

部署数据目录、端口、域名、时区和凭据由用户配置；本流程不会启动、替换或迁移现场容器。生产升级仍须固定摘要、备份并在站点副本验证。

## 包含内容

- 固定已验证基础镜像分发摘要和官方应用提交；新发行不把 CRM 永久锁死在 1.87.0。
- SQLite 3.54.0 官方源码与 SHA3-256 校验，验证 Python 实际链接库及中文物料分词参数。
- 普通重启不执行迁移，镜像/站点版本不一致时拒绝启动，升级必须显式授权。
- 升级前自动备份并验证数据库压缩流，备份位于 private/runtime_backups，不清理用户原备份目录。
- Redis/数据库就绪检查、短/默认队列与长队列分开、停机宽限。
- 全空目录默认初始化站点，支持手工覆盖初始化开关和密码；发现旧数据库与站点配置不匹配时停止，避免误建空系统。
- 不包含企业数据、公司配置、真实密码或备份；公司配置包独立保存在用户本机。

## 创建测试站点

Compose 默认使用独立命名卷和本机 8091 端口，用户可修改卷或在 Docker Desktop 手工映射宿主机目录；没有固定 Windows 路径。

全空目录默认 `INIT_SITE=1`，站点存在后不会重新初始化。默认内部站点名为 `erp.localhost`，数据库和管理员初始化密码默认 `Pass1234`（仅测试用途），均可通过环境变量覆盖。设置 `INIT_SITE=0` 可禁止创建新站点。密码文件方式仍支持，`DB_ROOT_PASSWORD_FILE` / `ADMIN_PASSWORD_FILE` 优先于环境变量。生产使用前应更换测试密码。

可配置参数包括 `IMAGE_NAME`、`HTTP_PORT`、`BIND_ADDRESS`、`SITE_NAME`、`DB_ROOT_PASSWORD`、`ADMIN_PASSWORD`、`TZ`、`INIT_SITE` 和 `RUN_MIGRATIONS`。已有数据库密码、站点身份及数据路径的更换需要配套迁移，不能把修改变量当作数据迁移。

## 已有站点升级

必须先备份并在副本测试。相同运行版本直接启动；第一次接入优化版或版本变化设置 RUN_MIGRATIONS=1。入口先检查降级风险、生成并验证备份，再安装缺失应用和迁移，成功后写入版本标记。

升级后将 RUN_MIGRATIONS 恢复为0。即使未清除该变量，只要标记一致也不重复迁移。迁移失败不写入新标记，容器退出，不能绕过检查强行启动。

不能仅把旧镜像换回去就视为数据库回退完成；需要恢复同一恢复点的数据库、附件与相匹配的代码。

## 验证与边界

GitHub Actions 检查构建、全新空站点、真实 ItemSearch 构建、重启跳过迁移、标准镜像空站点迁移、升级拒绝机制和升级前备份。通过后才发布独立优化标签；没有自动部署企业环境。

本优化保持单容器结构；持久化目录、端口、密码和主机资源属于部署层。不能靠镜像消除 Windows bind mount 的跨文件系统开销，也不保证业务保存耗时必然改善。

SQLite 来源：[官方源码下载](https://www.sqlite.org/download.html)。部署参数：[Docker Compose](https://docs.docker.com/reference/compose-file/services/)。
